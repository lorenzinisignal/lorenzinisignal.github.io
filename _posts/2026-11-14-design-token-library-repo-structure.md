[지난 글]({% post_url 2026-11-14-figma-design-tokens-to-bootstrap-and-tailwind %})에서 검토한 대로 Tailwind 라이브러리를 실제로 만들었습니다. 만들고 나서 가장 먼저 받은 질문이 이거였습니다.

> tailwind 폴더에 있는 값이 Tailwind 원본값인가요, 아니면 토큰값이 반영된 건가요?

저장소를 열어 봤을 때 바로 답이 나오지 않는다면 README가 부족한 것입니다. 구조를 어떻게 잡았는지, 그리고 이 질문의 답을 정리합니다.

## 값이 흐르는 방향을 폴더 이름으로

폴더를 세 개로 나누고, 값이 한 방향으로만 흐르게 했습니다.

```
tokens/     값의 출처 (사람이 고치는 곳)
scripts/    변환기
tailwind/   라이브러리 결과물
```

이렇게 나누면 "이 값을 고치려면 어디를 건드려야 하나"에 답이 하나뿐입니다. 항상 `tokens/`입니다.

### tokens/ — 값의 출처

| 파일 | 내용 | 고치는 주체 |
|---|---|---|
| `원본.json` | 디자인 툴에서 내보낸 토큰 | 다시 내보내 통째로 교체 |
| `extensions.json` | 원본에 없어 새로 만든 토큰, 그리고 수정 제안 | 사람이 직접 |
| `catalog.json` | 전체 토큰 목록 (구분·값·참조·클래스·근거) | 자동 생성 |

여기서 하나 중요한 결정이 있었습니다. **새로 만든 토큰을 원본 JSON에 섞지 않는 것.**

디자인 툴에서 내보낸 파일은 언제든 다시 내보내 통째로 교체됩니다. 거기에 직접 추가한 토큰이 섞여 있으면 교체할 때마다 사라집니다. 그래서 새 토큰과 수정 제안은 `extensions.json`에 따로 두고, 빌드할 때 둘을 합칩니다. 원본은 읽기 전용처럼 다룹니다.

### scripts/ — 변환기

디자인 툴이 내보낸 JSON은 CSS 프레임워크가 바로 읽을 수 있는 형식이 아닙니다. 그 사이를 메우는 스크립트입니다. 하는 일은 대략 이렇습니다.

- alias(다른 토큰을 가리키는 참조)를 끝까지 따라가 실제 값 찾기
- 이름 정리 (대소문자, 쉼표, 중복 단어, 오타 보정)
- px를 rem으로 변환
- 명암비 계산
- 깨진 참조, 이름 충돌, 기준 미달이 있으면 **빌드 중단**

마지막 항목이 생각보다 유용합니다. 토큰을 다시 내보냈는데 어딘가 깨졌다면, 조용히 잘못된 CSS가 나오는 대신 빌드가 멈추고 무엇이 문제인지 알려줍니다.

이름 변환 규칙은 스크립트 맨 위에 상수로 모아 뒀습니다. 규칙이 코드 여기저기 흩어지면 나중에 "이 클래스 이름이 왜 이렇게 됐지"를 추적할 수 없습니다.

### tailwind/ — 결과물

| 파일 | 내용 | 자동 생성 |
|---|---|---|
| `index.css` | 진입점 |  |
| `theme.css` | `@theme` 토큰 | **예** |
| `base.css` | 본문 글자, 기본 테두리색, 포커스 표시 |  |
| `components.css` | 버튼, 입력창, 테이블 등 컴포넌트 클래스 |  |

자동 생성 파일은 `theme.css` 하나뿐입니다. 나머지는 손으로 씁니다. 파일 맨 위에 "직접 고치지 말고 토큰을 고친 뒤 빌드하라"는 주석을 넣어 뒀습니다.

## 그래서, 그 폴더의 값은 어디서 왔나

**이 폴더에 Tailwind 자체 코드는 없습니다.** Tailwind 위에 얹는 설정과 컴포넌트 CSS만 있고, 값은 토큰에서 왔습니다. Tailwind 본체는 쓰는 쪽 프로젝트에서 따로 설치합니다.

값의 출처는 세 가지로 나뉩니다.

**1. 토큰으로 교체한 것** — 색상, 글자 스타일, 모서리 반경, 그림자.

Tailwind 기본값은 `--color-*: initial` 같은 줄로 아예 지웠습니다. 그래서 `bg-blue-500`을 쓰면 Tailwind의 파란색이 아니라 디자인 시스템의 blue/500이 나옵니다. `text-sm` 같은 Tailwind 기본 글자 크기 클래스는 동작하지 않습니다. 토큰에 없는 색과 크기는 쓸 수 없게 하려는 의도입니다.

**2. Tailwind 기본값을 유지한 것** — 간격 규칙(1단위 = 4px), 브레이크포인트, 전환 시간, 굵기 이름.

간격은 토큰 값이 전부 4px 배수로 떨어져서 기본 규칙 그대로 표현됩니다. 굳이 바꿀 이유가 없었습니다. 오히려 바꾸면 Tailwind 문서와 예제가 전부 안 맞게 됩니다.

**3. 새로 만든 것** — 토큰에 없던 상태 색, 포커스 링, 컴포넌트 높이 등.

임의로 만들지 않고 기존 팔레트 단계를 참조했습니다. 기준이 아예 없는 것(브레이크포인트 등)은 Tailwind 기본값을 따랐습니다.

## '원본'이라는 말이 모호했다

README에 "원본 값을 그대로 쓴다"고 적었는데, 이 문장이 질문을 부른 원인이었습니다. 저는 **디자인 토큰 원본**(명암비 수정안을 적용하지 않았다는 뜻)을 말한 건데, 읽는 쪽에서는 **Tailwind 원본**으로 읽을 수 있습니다.

같은 문서 안에 "원본"이 가리킬 수 있는 대상이 둘이면, 둘 다 매번 수식어를 붙여야 합니다. "원본 토큰", "Tailwind 기본값"처럼요. 지금은 README에 그 구분을 따로 적어 뒀습니다.

## 정리

- 폴더를 값이 흐르는 순서대로 나누면, 고칠 곳이 어디인지 묻지 않아도 됩니다.
- 디자인 툴에서 다시 내보낼 원본과 직접 추가한 토큰은 파일을 분리합니다.
- 자동 생성 파일에는 생성된 파일이라고 적어 둡니다.
- 프레임워크 설정 폴더를 두면 "이 값이 프레임워크 기본값인지 우리 값인지"를 누군가 반드시 묻습니다. 교체한 것, 유지한 것, 새로 만든 것으로 나눠 README에 적어 두면 한 번에 답이 됩니다.
- 한 문서에서 같은 단어가 두 대상을 가리키면, 수식어를 붙이거나 용어를 바꿉니다.
